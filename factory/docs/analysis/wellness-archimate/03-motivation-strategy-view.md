## How the elements were derived

- **Stakeholders** = the actors surfaced by the S-V-O decomposition (`02-structural-elements.md`):
  Member, Department of Health, Reward Partner/Aggregator, Programme Administrator/CMS author,
  Fraud & Integrity Analyst, Platform Operator.
- **Drivers / Assessments** = the *why* behind the 8 load-bearing invariants (health, engagement,
  reward-economy integrity, fraud risk, compliance, partner viability, auditability, maintainability)
  and the current-state pains that justify the architecture.
- **Goals / Outcomes** = the measurable targets, with Outcomes carrying the catalogue's concrete
  values (WeeklyScore=min(100,…), Points=score×10, <50ms eligibility, 30-day dispute window, etc.).
- **Principles / Constraints** = the 8 invariants split correctly: enduring architectural rules →
  **Principles** (frozen-on-publish, warehouse-not-SoT, verified-signal gate, financial-grade ledger,
  inline fraud guard, versioned event spine, typed-data scoring, idempotency, loose OLAP/OLTP);
  hard numeric/behavioural restrictions → **Constraints** (300s reservation, 5% holdback, 7y retention,
  irreversible withdrawal, score cap 100, DoH prize boundary).
- **Requirements** = 12 aggregate requirements, one per ABB cluster, each tracing to its BR group
  (the full 114 BRs roll up here; modelling all 114 in a motivation view would make it unreadable).
- **Strategy** = 12 Capabilities (the ABB clusters), 6 Courses of Action (the strategic *choices* the
  document makes), 4 Resources (scoring registry, partner network, data feeds, the points economy),
  and 1 member Value Stream (Identify → Enrol → Earn → Recognise → Redeem → Settle).

## Relationship scheme (ArchiMate metamodel-correct)

- Stakeholder **─association→** Driver · Value **─association→** Stakeholder.
- Assessment **─association→** Driver (assesses) and **─influence(+)→** Goal (motivates).
- Driver **─influence(+)→** Goal.
- Outcome **─realization→** Goal · Requirement **─realization→** Goal.
- Principle **─influence(+)→** Requirement (+ a few **─realization→** Goal for direct enablers).
- Constraint **─realization→** Goal and **─influence(−)→** Requirement (it restricts).
- Resource **─assignment→** Capability.
- **Strategy realization chain** (per the reference): Capability **─realization→** Course of Action
  **─realization→** Requirement. Every Requirement (r1–r15) is realized by exactly one Course of
  Action; every Course of Action is realized by ≥1 Capability — so no strategy element dangles.
- Capability **─serving→** Value Stream · Value Stream **─serving→** Member · Value Stream **─realization→** Value.

Realization always points from the more-concrete realizing element to the more-abstract realized one;
Influence carries a +/− modifier; this keeps the file valid against the ArchiMate 3.x relationship table.

## Business-level abstraction (solution kept out of Motivation & Strategy)

The source is a *solution-architecture* document, so the first extraction leaked implementation
detail into these layers. The Motivation & Strategy layers must be **technology-agnostic** — they
state *what the business wants and the strategic choices it makes*, not *how it is built*. A
rephrasing pass (`REPHRASE` in the generator) lifts each leaky element to its business intent;
IDs and relationships are unchanged, and the implementation specifics still live in the
requirements/rules catalogue (`00-…md`) where they will resurface correctly at the **Application /
Technology** layers in Phases 4–5. Examples:

| Element | Before (solution-laden) | After (business intent) |
|---|---|---|
| coa1 | Adopt the OLAP/OLTP seam (CDC + reverse-ETL) | Separate analytical insight from operational delivery |
| coa2 | Event-driven ABB decomposition on a versioned spine | Deliver as modular, independently-evolvable capability services |
| coa3 | Versioned strategy-registry scoring engine | Govern scoring as versioned, business-owned policy |
| coa4 | Two-phase reservation + double-entry ledger | Run rewards as financial-grade accounts |
| p2 | Warehouse is never source of truth for state/money | Operational & financial records are authoritative |
| p6 | Versioned event spine | Information shared between capabilities is consistent & traceable |
| p8 | Idempotency at value boundaries | No action is rewarded or charged twice |
| o3 | WeeklyScore = min(100, Σ daily-goal + …) | Scores computed consistently and reproducibly |

**Kept deliberately:** concrete values inside **Constraints** (e.g. score capped at 100, points =
score×10, 300 s reservation, 5% holdback, 7-year retention) — these are *business rules*, not
implementation, so they belong in the Motivation layer.
